# 网易云私信与多人一起听

根据协议证据实现目标项目的网络与业务层。本文不依赖某个播放器、UI 框架、宿主 API 或已登录账号；单独复制整个技能目录即可读取协议说明。源码链接是本仓库的可选证据定位入口，移植后可以用目标项目的实现替换。

## 先做这几个判断

- 目标是 **官方多人**：`multi/...` 与双人 `listentogether_*`、跟听 `isFLT=true` 分开，不能互相替代。
- 需要的是 **消息正文推送**、**联系人在线查询**还是**自身在线上报**。三者是不同能力；最后一项目前只有静态协议线索，没有单独桌面会话的因果实测。
- 判断“轮询”时区分对官方 HTTP 的查询、Mini 长连接接收，以及前端读取本地事件队列。
- 大整数从原始 JSON token 保留，不能先转 JavaScript `Number` 再转字符串。
- 业务成功要检查 `data.success`、`failedCode`、`data.result` 或确认消息 ID，不能仅看 HTTP 200。

## 实现与调试约束

1. 在目标项目的受控网络层处理 Cookie、IM token、校验令牌和固定端点；不把凭据、原始压缩包或任意 URI 调用能力暴露给 UI。
2. 账号切换使旧异步请求、通知游标、媒体目标和缓存失效。房间操作提交前重新确认房间、歌曲业务条目和权限。
3. 真账号读写的授权取决于当前任务。本文及历史测试授权不等于允许新测试向好友或房间发消息、推歌、收藏、删除或改变在线隐私。
4. 超时后的消息发送可能已经成功。先查询确认，不自动重发；客户端 `requestId` 去重只能证明本进程范围内的行为。
5. 报告结果时分别写“静态发现”“实现已接入”“模拟测试通过”“真实账号实测”。尤其不要把 Mini 登录成功写成私信已收到，也不要把在线查询写成在线上报已完成。

## 输出应保留什么

交付协议适配时，记录使用的端点、字段来源、成功判据、账号/房间变化的处理，以及实际执行的验证。继续研究时记录 APK/RN 包版本和哈希、类或方法、响应结构和结论限制；不提交 APK、反编译源码、凭据或私信原文。
